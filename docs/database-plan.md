# Relational Database Plan

## 1. Purpose and Status

This document proposes a maintainable Version 1 relational data model for the confirmed Socotra tourism website requirements. It is an architecture plan only; it does not modify or prescribe executable Prisma schema syntax.

The current Prisma datasource is SQLite and the schema contains no application models. PostgreSQL migration is a future operational option, not a Version 1 feature.

Version 1 supports English and Arabic and includes Instagram integration. Online payment remains excluded. The current localization layer is static and typed; future database-managed translations remain a planned extension.

Principles:

- Use explicit, typed models for known business concepts.
- Keep presentation components independent from Prisma records.
- Make routine content changes possible through the dashboard.
- Avoid untyped JSON blobs and premature generic-CMS abstractions.
- Preserve stable ordering and publication controls.
- Keep secrets outside database-managed public settings.
- Add future payment and localization models alongside current models rather than distorting Version 1.

## 2. Naming and Common Conventions

- Primary keys: opaque string IDs, generated by the application/ORM.
- Timestamps: UTC `DateTime` values named `createdAt` and `updatedAt`.
- Optional archive time: nullable `archivedAt`.
- Ordering: integer `displayOrder`, default `0`; lower values render first.
- Public visibility: explicit status or `isPublished`/`isActive`, never inferred from content.
- Text: plain text unless a specific sanitized rich-text format is later approved.
- URLs/paths: strings validated at the application boundary.
- Enums: use stable uppercase internal values and map them to friendly UI labels.
- Referential actions: explicitly documented rather than relying on provider defaults.
- Database records are mapped into domain/view models before reaching UI components.

## 3. Proposed Enums

### `PublicationStatus`

- `DRAFT`
- `PUBLISHED`

Use for `Tour`. Archival is represented separately by `archivedAt`; this avoids combining editorial state with lifecycle state.

### `BookingStatus`

- `NEW`
- `CONTACTED`
- `IN_PROGRESS`
- `CONFIRMED`
- `CANCELLED`
- `ARCHIVED`

**Recommendation:** implement this as an enum.

These values represent a controlled workflow used for filtering and reporting. An enum prevents spelling variants and invalid states. The values should remain intentionally small for Version 1. If a future client workflow requires configurable statuses, migrate to a status table then; do not add that complexity now.

`CONFIRMED` means an administrator has marked the inquiry accordingly. It is not an online payment state.

### `ContactRequestStatus` (future Contact implementation)

- `NEW`
- `IN_PROGRESS`
- `RESOLVED`
- `ARCHIVED`

This workflow is separate from `BookingStatus`: a general enquiry is not a
booking request and must not inherit booking confirmation or payment
semantics.

### `AdminRole`

- `ADMIN`

Version 1 has one role because exact roles and permissions are not confirmed. Retaining a role field creates a deliberate extension point. If multiple configurable roles and granular permissions are later approved, introduce normalized `Role`, `Permission`, and join tables in a migration.

### `HomepageSectionKey`

- `HERO`
- `WHY_SOCOTRA`
- `EXPERIENCE_HIGHLIGHTS`
- `FEATURED_TOURS`
- `FLIGHTS`
- `GALLERY`
- `INSTAGRAM`
- `FAQ`
- `TESTIMONIALS`
- `FINAL_CTA`

This enum controls known homepage section visibility/order. `TESTIMONIALS` defaults disabled because testimonials are unconfirmed.

### `InstagramCacheSource`

- `API`
- `PLACEHOLDER`

Allows the UI and admin area to distinguish live/cached API content from explicitly temporary fallback content.

### `SettingValueType`

Not recommended for Version 1 if using the explicit singleton `SiteSetting` model below. A generic key/value table would need `STRING`, `BOOLEAN`, `INTEGER`, and `JSON` types plus a validation registry, but would weaken relational guarantees. Add such a facility only for genuinely unpredictable settings.

### 4.6 `TourExclusion`

**Purpose**

Store one ordered excluded service/item per record.

Fields, relationships, indexes, timestamps, ordering, and deletion behavior match `TourInclusion`.

### Inclusions/exclusions decision

Use separate relational tables, not JSON.

Benefits:

- Independent add/edit/delete/reorder operations
- Straightforward form validation
- Stable ordering
- Provider-neutral data
- No whole-array overwrites
- Easier future translation per item

Two explicit tables are preferred over a single table with an `INCLUDED`/`EXCLUDED` discriminator because they preserve clear domain intent and keep simple dashboard operations easy to reason about. If future shared behavior materially outweighs clarity, they can be consolidated in a migration.

| `travelerCount` | Integer | Yes | Positive, bounded |

The user has confirmed the booking flow fields for architecture. Privacy notice, exact validation limits, and whether preferred date may be omitted remain **Client Information Required**. The implementation should collect no additional fields without approval.

- Optional many-to-one `Tour`

**Foreign key behavior**

- `onDelete: SetNull` for an exceptional physical tour deletion.

- Unique `reference`
- `(status, submittedAt)`
- `tourId`

**Payments extension**

Do not add payment fields in Version 1. A future `Payment` model can reference `Booking` with provider, external reference, amount, currency, status, and timestamps. This avoids redesigning the booking record while keeping payment concerns separate.

### 4.8 `Flight`

**Purpose**

Store independently ordered weekly flight schedule entries managed through `/admin/flights`. The public homepage reads only active entries; normal schedule changes require dashboard operations rather than code changes.

| Field | Type | Required | Default / constraint |
| --- | --- | ---: | --- |
| `id` | String | Yes | Generated primary key |
| `routeTitle` | String | No | Client Information Required |
| `operatingDay` | String | No | Exact day is Client Information Required |
| `departureLocation` | String | No | Client Information Required |
| `arrivalLocation` | String | No | Client Information Required |
| `departureTime` | String | No | Preserve client-facing local time text until timezone semantics are confirmed |
| `arrivalTime` | String | No | Same constraint |
| `airline` | String | No | Client Information Required |
| `flightNumber` | String | No | Stored only when provided by the client |
| `scheduleNotes` | String/Text | No | Approved schedule notes |
| `isActive` | Boolean | Yes | `false` |
| `displayOrder` | Integer | Yes | `0` |
| `createdAt` | DateTime | Yes | Current time |
| `updatedAt` | DateTime | Yes | Auto-updated; supplies “last updated” |

**Indexes**

- `(isActive, displayOrder)`

**Deletion**

Administrators may deactivate an entry to hide it temporarily or physically delete it when it is no longer needed. `Flight` has no dependent records in Version 1, so deletion has no cascade. Destructive deletion requires confirmation in the dashboard.

**Publication**

`isActive = true` is the public visibility rule. Public queries return active entries only, ordered by `displayOrder` with a stable tie-breaker. Nullable fields allow schedule records to be prepared before all client details exist, but activation must require an approved, meaningful display record and must never introduce defaults that look factual. The confirmed statement “flights operate twice weekly” and the approved change/reconfirmation disclaimer belong in typed homepage/site content; individual schedule details remain in `Flight`.

**Empty state**

No active records is a valid state. The homepage retains the twice-weekly statement and displays a clear schedule-unavailable/awaiting-approved-details message plus the visible disclaimer; it must not render a fabricated timetable. The current temporary status values are replaced by these records once approved schedule data is entered.

**Purpose**

Control enabled state and ordering for a fixed set of known homepage sections without storing arbitrary content blobs.

| Field | Type | Required | Default / constraint |
| --- | --- | ---: | --- |
| `id` | String | Yes | Generated |

### Homepage modeling decision

Use explicit structured models (`HomepageContent`, `HomepageHighlight`, `HomepageSection`) rather than one generic flexible table.

This gives:

- Typed forms and validation
- Predictable rendering
- Controlled section keys
- Easy content edits without page-code changes
- No arbitrary component or HTML injection
- A practical future locale dimension

A generic block CMS would add excessive abstraction for a single-developer MVP and make field-level validation harder. New fundamentally different sections may require a small schema and code change, which is appropriate for a new product capability.

**Purpose**

**Unique constraints and indexes**

- Prefer unpublishing over deletion.
- Production readiness requires approved About content and applicable legal content.
- Page components receive a typed DTO and never contain client copy.

**Why this is not a generic CMS**

`PageContent` is restricted to three confirmed informational pages and a fixed field contract. It does not select arbitrary components or store page-builder JSON. If a future page needs materially different structured content, add an explicit model or relation.

**About content refinement**

The implemented About page has a defined structure rather than one untyped
body: hero, ordered editorial sections, ordered feature sections/items,
highlights, CTA, images/alt text, publication state, and SEO. No database
integration exists yet; client-provided content currently uses a centralized
typed static adapter. Before dashboard implementation, the database design
should extend the fixed `ABOUT` aggregate with explicit typed section and item
relations (or equivalent validated fields), including stable keys, order,
publication flags, media references, and locale. It must not become an
arbitrary page-builder blob.

Publication validation must require alt text for meaningful images and reject
missing media references. Content governance must exclude unsupported claims,
including the Arabian leopard on Socotra and the unverified UNDP “Top 5”
ranking, while ensuring legends remain clearly labelled as legends.

**Cardinality**

- Singleton row, enforced by a stable singleton key or service-level invariant.

**Typing decision**

Use explicit nullable columns, not a generic `key/value` table. This keeps validation and migration behavior clear. If notification recipients require multiple values, use a related `NotificationRecipient` table rather than an untyped JSON array.

**Secrets**

Never store Meta tokens, session secrets, email API keys, encryption keys, or database URLs here. Public settings may be safely selected into a limited DTO; protected settings require an admin DTO.

| `caption` | String/Text | No | Sanitized |
| `mediaType` | String/enum | Yes | Validated supported types |
| `mediaUrl` | String | Yes | Valid URL |
| `thumbnailUrl` | String | No | Valid URL |

| `fetchedAt` | DateTime | Yes | Current time on refresh |
| `expiresAt` | DateTime | Yes | Refresh TTL deadline |
| `isPublished` | Boolean | Yes | `false` for unapproved placeholders by default |
| `createdAt`, `updatedAt` | DateTime | Yes | Standard timestamps |

**Unique constraints/indexes**

- Unique nullable `externalId` for API content; verify target database behavior during migration
- `(source, isPublished, displayOrder)`
- `expiresAt`

**Deletion**

- API refresh may upsert current posts and expire/remove obsolete cached records according to retention policy.
- Placeholder records are managed separately and are never overwritten as if they were API records.

**Cache expiration**

The service checks `expiresAt`. If fresh, it returns cached records. If stale, it attempts a server-side refresh. On refresh failure, it may return stale API cache within a documented stale-if-error window; otherwise it returns approved placeholder data or disables the section.

### Instagram strategy decision

**Recommendation:** use a server-only Instagram adapter plus database cache.

The current implementation does not create cache records or call Meta. It
renders explicitly temporary centralized local post data and hides profile or
post actions when URLs are absent. This static source is an adapter-compatible
development state, not simulated live API data.

Compared with request-time API fetching:

- The homepage is not dependent on Meta latency or uptime.
- Cached content survives process restarts and deployment instances.
- Administrators can see refresh status.
- Rate limits are easier to control.
- Stale-if-error behavior is predictable.

Tradeoffs:

- Cache refresh and cleanup logic must be maintained.
- External media URLs can expire; refresh must account for current Meta behavior.
- Database content is eventually consistent, not instantly live.

A framework memory cache alone is simpler but less reliable across server instances and deployments. Direct browser fetching is rejected because it risks credentials, weakens control, and couples the homepage to the external service.

### 4.19 `IntegrationState` (supporting recommendation)

**Purpose**

Store non-secret operational metadata for Instagram.

Fields: `id`, unique `integrationKey` (`instagram`), `isEnabled`, `lastAttemptAt`, `lastSuccessAt`, `lastErrorCode`, sanitized `lastErrorMessage`, `createdAt`, `updatedAt`.

No token or secret value is stored. This provides admin status without overloading `SiteSetting`.

## 6. Slug Strategy

- Generate an initial slug from the client-approved tour title.
- Normalize to lowercase ASCII-compatible, hyphen-separated form.
- Require uniqueness.
- Allow administrators to edit the slug with validation and a change warning.
- Never silently change a published slug when the title changes.
- Version 1 does not require redirect history, but a future `TourSlugRedirect` model is recommended if published URLs change.
- Reserved application route segments must be rejected.
- Public lookups require `status = PUBLISHED` and `archivedAt = null`.

## 7. Ordering Strategy

Every ordered collection uses integer `displayOrder`.

Reorder operations:

1. Accept the complete ordered list of IDs within the parent scope.
2. Verify all IDs belong to that scope.
3. Update positions in one transaction.
4. Normalize to predictable increments or contiguous integers.
5. Read using `displayOrder` plus `createdAt` or ID as a stable tie-breaker.

This applies to tours, itinerary days, tour images, inclusions, exclusions, flights, gallery items, FAQs, homepage highlights, sections, notification recipients, and placeholder Instagram items where applicable.

## 9. Cascading Deletion Summary

| Parent deletion | Child behavior |
| --- | --- |
| Tour physically purged | Cascade itinerary days, images, inclusions, exclusions; set booking `tourId` to null |
| Tour archived | Retain every relation |
| HomepageContent physically removed | Cascade highlights and section controls |
| PageContent removed | No child cascade; prefer unpublishing |
| SiteSetting physically removed | Cascade social links and notification recipients; singleton removal should normally be blocked |
| AdminUser removed | No current child cascade; prefer deactivation |
| Media record removed | Do not automatically delete remote asset without reference check |

## 10. SQLite-to-PostgreSQL Migration

Keep migration practical by:

- Avoiding provider-specific SQL, collation assumptions, and SQLite-only functions.
- Using ORM-supported scalar types and explicit relations.
- Storing money as integer minor units rather than floating point.
- Using UTC timestamps.
- Avoiding JSON for core content.
- Normalizing repeatable content into child tables.
- Validating case-normalized unique values in the application.
- Testing nullable unique behavior, enum migration, and date semantics on PostgreSQL before cutover.
- Keeping repository interfaces independent from Prisma/provider details.
- Using migration scripts and a rehearsed data export/import rather than changing the datasource in place without verification.
- Moving production media outside the local filesystem so database migration does not strand assets.

SQLite remains suitable for the planned foundation and a small MVP deployment only if the chosen production environment supports durable storage, backups, and the expected write concurrency. Hosting constraints must be confirmed before deployment. PostgreSQL should be selected before launch if the platform uses ephemeral storage, multiple application instances, or higher concurrent writes.

## 11. Future Localization

Version 1 stores English (`en`) only. To avoid rebuilding:

- Keep `locale` on singleton/page content where appropriate.
- Keep UI labels in a central application message layer rather than scattering literals.
- When multilingual scope is approved, introduce translation tables such as `TourTranslation`, `FaqTranslation`, and `SiteSettingTranslation` keyed by entity and locale. `HomepageContent` and `PageContent` already have a locale boundary.
- Do not add empty translation tables in Version 1.
- Slug localization and locale-prefixed routes require a separate approved URL strategy.

# Future Localization Mapping

The current bilingual static adapter keeps stable entity IDs, slugs, prices, ordering, publication state, and image paths outside translated presentation content. A later Prisma design should preserve one business entity and add locale-keyed translation records for content-rich models (for example `TourTranslation`, `FaqItemTranslation`, and page-section translations) with a composite unique constraint on entity ID plus locale. Small structured settings may use explicitly typed localized fields where justified.
